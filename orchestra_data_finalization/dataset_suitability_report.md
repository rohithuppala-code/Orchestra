# SILO-BENCH Suitability Report for ORCHESTRA

> **Project:** ORCHESTRA — Emergent Organizational Evolution in Autonomous AI Agent Societies
> **Benchmark:** SILO-BENCH v1.0.0 (Zhang et al., 2026, arXiv:2603.01045)
> **Date:** 2026-10-09
> **Status:** Evidence-based evaluation from full source code inspection

---

## Executive Summary

SILO-BENCH is **suitable as ORCHESTRA's primary task benchmark** — but with a critical distinction. It provides an excellent *task substrate* (30 coordination problems at 6 agent scales with 3 communication protocols) over which organizational behavior can be studied. However, **no behavioral data exists in the repository**. All data relevant to ORCHESTRA's core research questions (role emergence, leadership, organizational structure) must be **generated by running experiments** and then **extracted from the resulting logs**.

## 2. Evaluation Against ORCHESTRA Research Objectives

### 2.1 Emergent Roles and Specialization

**Classification: Derivable** (from experiment execution logs)

**Evidence:**
- The system prompt in [`prompts.py`](file:///c:/Users/sairo/OneDrive/Documents/UROP/silo-bench/src/utils/prompts.py#L272-L292) explicitly states: *"You are a member of a multi-agent system"* — **no roles are pre-assigned**. All agents receive identical system prompts (differing only in `agent_id`).
- The user prompt in each `agent_configs[i].user_prompt` gives only data and a generic algorithm description — no role assignment.
- Each agent independently decides *who* to message (P2P), *what* to broadcast, or *what files* to write/read.

**What would constitute evidence of role emergence:**
- An agent that consistently aggregates others' data → "coordinator" role
- An agent that only sends its local result and waits → "worker" role
- This must be derived from **per-agent log files** (`logs/agent-NNN.jsonl`) generated during experiments

**Constraint:** The task descriptions include an "Algorithm" section with coordination hints (e.g., *"Topology: Star/Tree aggregation → broadcast"*). This guidance may constrain truly free emergence. The agents are told the *optimal* topology, though they are free to ignore it. ORCHESTRA must acknowledge this as a confound.

### 2.2 Leadership and Influence

**Classification: Derivable** (from experiment communication logs)

**Evidence:**
- P2P protocol ([`msg/tools.py`](file:///c:/Users/sairo/OneDrive/Documents/UROP/silo-bench/src/msg/tools.py#L13-L42)) records `sender_id` and `recipient_id` for every message → directed communication graph is fully reconstructable.
- The `AgentState` model ([`models.py` L48-56](file:///c:/Users/sairo/OneDrive/Documents/UROP/silo-bench/src/models.py#L48-L56)) tracks `messages_sent`, `messages_received`, `files_written`, `files_read` per agent.
- The `LogEvent` model ([`models.py` L189-201](file:///c:/Users/sairo/OneDrive/Documents/UROP/silo-bench/src/models.py#L189-L201)) records every tool call with parameters (including target agent IDs).

**How to derive leadership:**
- From P2P logs: identify agents with high out-degree (many outgoing messages) and centrality in the communication graph
- From SFS logs: identify agents whose files are read most frequently by others
- From submission timing: identify agents who submit early vs. wait for others

**Limitation:** The framework does not track *influence* in the sense of which agent's data was ultimately used in the final answer. This would require content analysis of messages, which is possible from the logged `response` and `content` fields but would need custom post-processing.

### 2.3 Communication and Coordination Patterns

**Classification: Derivable** (richly logged by existing framework)

**Evidence:**
- Every tool call is logged via `_log()` in [`engine.py` L56-59](file:///c:/Users/sairo/OneDrive/Documents/UROP/silo-bench/src/engine.py#L56-L59) to `logs/agent-NNN.jsonl` with: `round`, `event` type (`llm_request`, `llm_response`, `tool_call`, `tool_result`, `submitted`), `agent_id`, full `parameters`, and `result`.
- P2P messages are persisted as individual JSON files in `rounds/round-NNNNNN/env/messages/` with `sender_id`, `recipient_id`, `content`, `timestamp`.
- Broadcast messages are persisted in `rounds/round-NNNNNN/env/broadcasts/` with `sender_id`, `content`, `timestamp`, `broadcast_id`.
- SFS writes are persisted in `rounds/round-NNNNNN/env/shared_kv.json` with `modified_by`, `modified_at_round`, and `content`.
- Communication Density (D) metric is already computed: `D = Σ_i m_i / N(N-1)` in [`metrics.py` L238-263](file:///c:/Users/sairo/OneDrive/Documents/UROP/silo-bench/src/utils/metrics.py#L238-L263).

**Strength for ORCHESTRA:** This is the most data-rich area. The full communication graph per round can be reconstructed, enabling analysis of topology evolution, information flow, and coordination strategy changes over time.

### 2.4 Organizational Structure and Stability

**Classification: Requires Extension**

**Evidence:**
- The framework produces **per-round snapshots** of communication, which enables tracking of communication topology evolution across rounds within a single experiment.
- However, there is no built-in concept of "organizational structure" — this must be inferred from communication patterns.
- The round-based architecture (messages in round *t* visible in round *t+1*, per [`prompts.py` L68](file:///c:/Users/sairo/OneDrive/Documents/UROP/silo-bench/src/utils/prompts.py#L68)) naturally creates temporal structure suitable for studying stability.

**What ORCHESTRA must add:**
- Post-processing to extract communication graphs per round and track structural metrics (centrality, clustering coefficient, hierarchy measures) over time.
- Repeated experiments (same task, different random seeds or model temperatures) to measure organizational stability across runs.

### 2.5 Adaptation and Recovery

**Classification: Requires Extension**

**Evidence:**
- The current framework has **no mechanism for agent removal, communication disruption, or perturbation** during execution. The `run_round()` function in [`engine.py` L203-420](file:///c:/Users/sairo/OneDrive/Documents/UROP/silo-bench/src/engine.py#L203-L420) iterates over all agents every round with no support for dynamic agent addition/removal.
- All three protocol implementations assume a fixed `num_agents` throughout execution.
- The P2P `send_message` validates `target_id < num_agents` — there is no "agent offline" state.

**What ORCHESTRA must add:**
- Modify the execution loop to support agent dropout (skip certain agents in certain rounds)
- Modify message delivery to simulate communication failures (drop messages, add delays)
- These are **engineering extensions to the framework**, not to the benchmark data itself

### 2.6 Collective Task Performance

**Classification: Available** (metric definitions exist) + **Derivable** (actual values require experiments)

**Evidence:**
- Four metrics are defined and implemented in [`metrics.py`](file:///c:/Users/sairo/OneDrive/Documents/UROP/silo-bench/src/utils/metrics.py):
  - **S (Success Rate):** fraction of agents with correct answer ([L45-78](file:///c:/Users/sairo/OneDrive/Documents/UROP/silo-bench/src/utils/metrics.py#L45-L78))
  - **P (Partial Correctness):** continuous quality score, tailored per level ([L96-211](file:///c:/Users/sairo/OneDrive/Documents/UROP/silo-bench/src/utils/metrics.py#L96-L211))
  - **C (Token Consumption):** total tokens / max rounds ([L214-229](file:///c:/Users/sairo/OneDrive/Documents/UROP/silo-bench/src/utils/metrics.py#L214-L229))
  - **D (Communication Density):** messages / N(N-1) ([L238-263](file:///c:/Users/sairo/OneDrive/Documents/UROP/silo-bench/src/utils/metrics.py#L238-L263))
- The `evaluate()` function in [`engine.py` L440-533](file:///c:/Users/sairo/OneDrive/Documents/UROP/silo-bench/src/engine.py#L440-L533) automatically computes and writes all metrics to `results.json` after each experiment.
- The analysis script [`analyze.py`](file:///c:/Users/sairo/OneDrive/Documents/UROP/silo-bench/src/analyze.py) aggregates results across experiments.
- **However, zero actual performance data exists** — the `workspace/` directory does not exist in the downloaded repo.

## 3. Critical Design Considerations for ORCHESTRA

### 3.1 The System Prompt Contains Coordination Hints

The `task_description` field in every benchmark JSON includes algorithm hints and suggested topology. For example, `I-01` (Global Max) says:

> *"Topology: Star/Tree aggregation → broadcast. All agents must submit the same final answer."*

And the `metadata.optimal_topology` field explicitly states the optimal communication structure. While agents can choose to ignore this guidance, it **biases against truly emergent organization**. ORCHESTRA should:

1. **Acknowledge this as a controlled variable** — the hints represent "task knowledge" that real organizations also possess.
2. Consider creating **modified task descriptions without topology hints** to study unconstrained emergence.
3. Compare organizational emergence *with* and *without* hints as an experimental condition.

### 3.2 All Agents Receive Identical Instructions

The system prompt ([`prompts.py` L272-292](file:///c:/Users/sairo/OneDrive/Documents/UROP/silo-bench/src/utils/prompts.py#L272-L292)) is symmetric across agents — only `agent_id` differs. This is **ideal for ORCHESTRA** because any differentiation in behavior must be emergent, not assigned.

### 3.3 Round-Based Synchronization Constrains Temporal Dynamics

Communication follows strict round-based synchronization: messages sent in round *t* are received in round *t+1*. This creates a discrete, synchronous communication model. Real organizations often have asynchronous communication. ORCHESTRA should note this as an environmental constraint on the organizational dynamics being studied.

### 3.4 No Persistent Memory Across Tasks

Each task execution is independent. There is no mechanism for agents to carry organizational experience from one task to another. Studying *organizational evolution* (learning over multiple tasks) would require extending the framework.

## 5. Conclusion

SILO-BENCH is **the right foundation** for ORCHESTRA. Its role-free design, scalable agent counts (2–100), three communication protocols, and comprehensive logging infrastructure make it uniquely suited for studying emergent organizational behavior. The critical understanding is that **SILO-BENCH provides the experimental testbed, not the experimental data** — all behavioral data must be generated through experiment execution, and ORCHESTRA-specific analysis tools must be built on top of the existing log format.
